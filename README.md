# グラフ畳み込みネットワークを用いた赤信号待ち台数予測による信号制御手法の研究

応用情報工学科 高橋福田研究室 / 満永 匠翔（指導教員: 高橋 聖 教授）

このリポジトリは、交通シミュレータ SUMO 上で再現した富山県昭和町の街モデルを使い、
**GCN（グラフ畳み込みネットワーク）で赤信号待ち台数を予測し、その結果で信号を制御する**
一連のプログラムを置いている。

---

## 1. 研究の目標

- **背景** … 都市問題の一つに交通渋滞がある。緩和には各交差点の信号機を交通需要に合わせて
  制御する必要がある。リアルタイムに交通需要を把握するセンサは存在するが、
  **取得した情報をもとに信号機を制御する手法は確立されていない。**
- **目的** … 交通流の円滑化を目的として、**信号機の動的制御手法を提案し、効果を検証する。**
- **既存研究との違い** … GCN による交通量予測が高精度に可能であることは示されているが、
  **予測した情報に基づく信号制御の検証がされていない。** 本研究はそこを埋める。

### 評価指標

| 指標 | 定義 |
| --- | --- |
| **待ち台数** | 各道路のエッジ上で `speed <= 0` になった車両の台数（サイクルごと） |
| **遅れ時間** | その車両が停車していた秒数の総和（1ステップ = 1秒で累積） |

集計は **対象交差点(J) / 他交差点 / 街全体** の3区分、および **全24h / 6〜19時** の2窓で行う。

### 現時点の到達点（2026-09 時点）

- 予測: 赤信号を前半・後半に2分割した待ち台数を1サイクル先予測。
  RMSE は 道路1 前半1.19台 / 後半1.34台、道路5 前半1.11台 / 後半0.76台。
- 制御: 対象交差点Jで **遅れ時間 −4.3%**（一般手法のギャップ感応制御 −2.4% を上回る）。
  ただし **待ち台数 −7.5%** はギャップ感応の −18.9% に及ばない。
- 街全体では両手法とも改善は見られず、削減分が周辺交差点へ移動する傾向がある。

→ 最新かつ最良の構成と、これまでに試した全パターンの結果は
  **[制御/README.md](制御/README.md)** に集約している。

## 2. 全体の流れ

```text
 ┌──────────┐      ┌──────────┐      ┌──────────┐
 │  計測/   │ ───> │  予測/   │ ───> │  制御/   │
 │ SUMOで   │ CSV  │ GCNを    │ .pth │ SUMO上で │
 │ 待ち台数 │      │ 学習     │ .pkl │ 予測して │
 │ を収集   │      │          │      │ 信号制御 │
 └──────────┘      └──────────┘      └──────────┘
                                           │
                                     ┌─────┴─────┐
                                     │ 発表/     │
                                     │ レジュメ/ │
                                     └───────────┘
```

1. **計測** … SUMO を走らせ、9道路それぞれの「赤信号を分割した各区間の停車台数」を
   CSV に落とす。これが学習データになる。
2. **予測** … その CSV で GCN を学習し、`.pth`（重み）と `scaler*.pkl`（正規化）を出力。
3. **制御** … SUMO を走らせながら学習済みモデルで次サイクルを予測し、J交差点の青時間を
   増減させる。制御なし・ギャップ感応制御という比較用ベースラインも同じプログラムに
   モードとして持つ。
4. **発表 / レジュメ** … 結果をスライドと発表概要にまとめる。

**計測と制御で「測り方」を一致させることが最重要。** 学習データと制御時の入力が
別の量になっていると、モデルは正しく動かない（[制御/README.md](制御/README.md) の
「制御方法の詳細仕様」を参照）。

## 4. 実装時の注意（フォルダ横断）

個別の注意は各 README にあるが、**どのフォルダでも踏みやすい**のは以下。

### 4.1 パス

- 現行の ★付き・番号付きスクリプトは **スクリプトの置き場所からの相対パス**で解決する。
- **旧スクリプトの多くは絶対パス直書き**（`C:\Users\Tsukasa\…` や `C:\Users\tslab\…`）。
  別PCでは動かない。新しく書くときは絶対パスを埋め込まないこと。
- フォルダを 計測 / 予測 / 制御 の3構成へ整理した際、`予測モデル/` の場所が変わって
  制御側が `FileNotFoundError` になった事故がある。移動したらパスの追従を確認する。

### 4.2 文字コードと改行コード

- CSV の文字コードが**混在している**（`utf-8` / `utf-8-sig`(BOM付) / `cp932`）。
  読み込みは `utf-8-sig` にしておくと BOM の有無どちらも通る。
- **改行コードはファイルごとに CRLF / LF が混在している。** このリポジトリは
  `core.autocrlf=false` で `.gitattributes` も無いため、**編集時に改行コードを
  書き換えると全行が差分として記録される**（実際に1ファイル 6,301行の差分が出た）。
  編集前後で改行コードが変わっていないか確認すること。
- **日本語パスで壊れるツールがある。** `latexmk` は Perl の `chdir` が CP932 で壊れるため
  使えない（`platex` + `dvipdfmx` を直接叩く）。

### 4.3 学習と制御の一致

- 制御側の前処理（正規化 → 対象ノードの `ALPHA` 倍 → 逆正規化）は
  **学習時と完全に同じ順序**でなければならない。
- モデルクラスの定義も学習スクリプトと一致必須。層構成が違うと `load_state_dict` は
  通っても出力が無意味になる。
- **入力の「量」の定義を取り違えないこと。** 赤分割モデルの入力は
  「各車が初めて停車した時刻を区間にビン分けした台数（非累積）」であり、
  「赤中の各時点で停車している台数（＝待ち行列長・累積）」ではない。
- 赤2分割モデルの学習データは **130s 固定サイクル**で作られている。制御時の
  時間帯別サイクル（100〜130s）とは条件が違う点に注意。

### 4.4 消してはいけないもの

- `予測/予測モデル/0. 制御用_待ち台数単体(3.22)/道路{1,5}/` … 現行スクリプトからも
  参照されているため削除しないこと。
- `発表/中間報告/` のスライドで、アニメーションの重ね図になっている図形。
  削除すると `<p:timing>` の参照が切れて **PowerPoint がファイルを開けなくなる**
  （実際に一度壊している）。消したいときはテキストだけ書き換える。

### 4.5 実行時

- 制御プログラムの出力先は **環境変数 `R2_SUFFIX` で分けられる。** 途中で打ち切る実行や
  試験的な設定では**必ず指定する**（既存の24h結果を上書きしないため）。
- 24時間走行は 1方式あたり **約16分**。短時間で挙動だけ見たいときは `R2_END` を使う。

## 5. git の運用ルール

### 5.1 上げるもの / 上げないもの

`.gitignore` は「いったん全部除外し、必要な拡張子だけを許可リストで戻す」方式。
**git に上げるのはプログラムとドキュメントのみ。**

| 上げる | 上げない |
| --- | --- |
| `*.py` / `*.md` / `*.sumocfg` | シミュレーション結果 CSV・図（`制御/csv掃き出し/` 約424MB） |
| `予測/新環境_隣接行列.csv` | 学習済みモデル（`.pth` / `.pkl`）・学習用データ |
| `制御/現示時間/*.csv`、`計測/*.txt` | スライド・図表（`発表/` 約280MB。README のみ追跡） |
| | `レジュメ/`（Overleaf が正本）、`没/`、`.history/`、`__pycache__/`、`.vscode/` |

**この方針は変更しない。** 結果を git に入れるとリポジトリが肥大し、
履歴からは消せなくなるため。

### 5.2 結果は README に残す

結果 CSV を上げない代わりに、**走らせたら [制御/README.md](制御/README.md) の
「走行記録」に1行追記する。** 記録する内容は

- **日付**
- **設定**（重み・モード・変更点）
- **実行方法**（環境変数をそのまま書く。これで再現できる）
- **出力先フォルダ名**（ローカルのどこに結果があるか）
- **結果の一言**（「最良」「悪化」「効果なし」など）

これを守れば、結果そのものが git に無くても「いつ何を試して何が分かったか」は残る。

### 5.3 ブランチとコミット

- **成果は `main` にコミットして push する。** 手元に未コミット・未 push の変更を
  溜めない。
- **試験的な変更はブランチを切る**（例: `fix/adjust-cycle`）。
  - うまくいったら `main` へマージする。
  - **ダメだった場合も、捨てずにブランチにコミットして残す。** 否定的結果も研究の
    成果であり、同じことを再び試すのを防げる。`main` にはマージせず、
    **README に「試したが不採用」と理由・数値を書く。**
- コミットメッセージは、**何を変えたか**だけでなく **なぜそうしたか / 結果どうだったか**
  を書く。後から経緯を追えるようにするため。
- `main` は `origin/main`（<https://github.com/mitsunagac/kenkyu>）へ push する。
