# 制御フォルダ README

SUMO（富山・昭和モデル）上で J 交差点の信号を制御するプログラム群。
`予測/` で学習した GNN モデル（`.pth` + `scaler*.pkl`）を読み込み、次サイクルの待ち台数を
予測して青時間を増減する。制御なし・ギャップ感応制御という比較用のベースラインも同じ
プログラムの中にモードとして持っている。

共通の考え方:

- **対象交差点は J**。道路1（主道路）= phase0、道路5（従道路）= phase5 の青を伸縮する。
- **delta**（青の増減秒数）を1サイクルごとに決め、`スケジュール青 + delta` を設定する。
  前サイクルの結果に足し込む（compound する）ことはしない。
- サイクル長は**時間帯別**（0-7時 100s / 7-8時 130s / 8-17時 110s / 17-19時 130s / 19-24時 100s）。
  J 以外の信号は各サイクル長にスケールしたプログラムを事前生成して切り替える。
- delta を入れ続けるとサイクル長がドリフトするので、**累積オフセット補正**（累積±20sで
  ±10s 押し戻す調整サイクル）を入れている。

## 可動範囲（青時間・サイクル長のずれの上限）

目標サイクル長が 100s でも 130s でも、**ずれの上限は絶対秒数で一定**にしている。

| 対象 | 上限 | 定数 |
| --- | --- | --- |
| 各青フェーズ（phase0 / phase5）の「その時間帯のスケジュール青」からのずれ | **±10s** | `J_GREEN_DEV_CLAMP` |
| J のサイクル長の「その時間帯の目標サイクル長」からのずれ | **±10s** | `J_CYCLE_DEV_CLAMP`（`R2_CYCLECAP` で変更可） |
| 青の絶対下限 | 5s | `J_MIN_GREEN` |

phase0 と phase5 は独立に制御されるため、放っておくと両方が同じ向きに振れてサイクル長のずれが
最大 ±20s になる。そこで delta を決めるとき `clamp_delta_for_cycle()` で
**もう一方のフェーズが既に使っている分を差し引いて**枠内に収める（切り詰めた分は累積にも乗せない）。
ギャップ感応制御も同じ枠を使い、`green_bounds_for_phase()` が返す範囲内でしか青を切らない。

各サイクル長でのスケジュール青と可動範囲:

| 目標サイクル | phase0（道路1） | phase5（道路5） |
| --- | --- | --- |
| 100s | 53s（43〜63s） | 19s（9〜29s） |
| 110s | 58s（48〜68s） | 24s（14〜34s） |
| 130s | 68s（58〜78s） | 34s（24〜44s） |

※ 括弧内は相手フェーズのずれが0のときの範囲。相手が+10s使っていれば上限側が10s狭まる。
5秒の絶対下限に引っかかるケースは全サイクル長で発生しない（最も厳しい100sのphase5で9s）。

出力は `csv掃き出し/<制御モード名>/` 配下（予測結果・フェーズ時間・遅れ時間・無駄青など）。

## 現在の最新かつ最良の構成（2026-09-18 時点）

**赤2分割GNN予測制御・需要重み付け方式、重み x1 = 0.99 / x2 = 0.9。**

```bash
cd 制御/新環境用
R2_MODE=prediction R2_X1=0.99 R2_X2=0.9 python "5. 信号制御_赤2分割.py"   # 提案手法（最良）
R2_MODE=gap  python "5. 信号制御_赤2分割.py"                              # 比較対象（ギャップ感応）
R2_MODE=none python "5. 信号制御_赤2分割.py"                              # 基準（制御なし）
```

24時間走行の結果（基準＝制御なし）:

| 方式 | 対象交差点J 待ち台数 | 対象交差点J 遅れ時間 | 街全体 待ち台数 | 街全体 遅れ時間 |
| --- | --- | --- | --- | --- |
| ギャップ感応（一般手法） | **−18.9%** | −2.4% | −2.2% | +1.5% |
| 提案手法 x1=0.99 / x2=0.9 | −7.5% | **−4.3%** | +0.3% | +0.2% |

- **遅れ時間では提案手法が最良**（ギャップ感応の −2.4% を上回る）。発表ではここを主張する。
- **待ち台数ではギャップ感応が最良**で、提案手法は及ばない。ギャップ感応が青の最中に
  車群の途切れを見て切れるのに対し、提案手法は1サイクル前に青時間を決めるため。
- 街全体はどちらもほぼ中立（対象交差点の削減分が周辺交差点へ移動する）。

重みは x1 > x2（赤の前半を重く見る）が必須。x2 を上げすぎる・ピーク時に x1 を 1.5 へ
上げる、はいずれも悪化した（下の走行記録を参照）。

## 制御方法の詳細仕様（これだけ読めば再実装できる粒度）

対象は **赤2分割GNN予測制御（需要重み付け方式）**。実装は
`新環境用/5. 信号制御_赤2分割.py` + `新環境用/赤2分割_制御コア.py`
（サイクル長と計測エッジ定義は `新環境用/赤3分割_制御コア.py` から import して共用）。

### 0. 全体の流れ

```
毎シミュレーションステップ（1秒）:
  1. 全9道路の「赤2分割」を実時間で計測（RedSplit2Tracker.step）
  2. ある道路の赤が終わって2分割が確定したら、その道路について:
       a. 全9道路の最新2分割 [9,2] を入力に GNN で次サイクルの [t3,t4] を予測
       b. [t3,t4] から delta（青の増減秒数）を計算
       c. delta を可動範囲へクランプ
       d. 調整サイクルの判定（累積が閾値を超えたら次サイクルは押し戻し）
       e. 「その時間帯のスケジュール青 + delta」を SUMO の J のロジックへ書き戻す
  3. 時間帯が変わったらサイクル長を切り替える（J 以外の信号も含む）
```

**制御対象は J 交差点のみ**。他の信号は時間帯別サイクル長のスケーリングだけ行う。

| 呼び名 | 道路ID | J のフェーズ番号 | 備考 |
| --- | --- | --- | --- |
| 主道路 | 道路1 | 青 = **phase 0** / 黄 = phase 1 | |
| 従道路 | 道路5 | 青 = **phase 5** / 黄 = phase 6 | phase 6 を青と扱うのは旧ネットの名残で誤り |

### 1. 赤2分割の計測（全9道路・毎ステップ）

モデルの入力は **9道路すべて** の2分割値なので、制御対象の1・5以外も測る。

計測対象エッジ（`MEAS_CONFIG`。`divisor` は車線数ぶんの割り算）:

| 道路 | 信号 | 青/黄 phase | エッジ | divisor |
| --- | --- | --- | --- | --- |
| 1 | J | 0 / 1 | `E24`, `-E23`, `-E33` | 2 |
| 2 | E | 0 / 1 | `E40`, `-E22` | 2 |
| 3 | F | 0 / 1 | `E3`, `E1`, `-E34`, `E35` | 2 |
| 4 | I | 0 / 1 | `E57` | 2 |
| 5 | J | 5 / 6 | `E37`, `E36` | 2 |
| 6 | J | 5 / 6 | `-E25`, `-E69` | 2 |
| 7 | K | 0 / 1 | `155398822#14`, `155398822#13` | 2 |
| 8 | M | 0 / 1 | `E31`, `E30` | 2 |
| 9 | N | 0 / 1 | `E20`, `E19` | 2 |

アルゴリズム:

1. **赤の開始** … その道路の**黄が終わった瞬間**（前ステップのフェーズ == yellow かつ
   今のフェーズ != yellow）。`red_start = sim_time` を記録。
2. **赤の間** … 対象エッジ上の各車について、**初めて `speed <= 0.0` になった時刻**の
   「赤開始からの経過秒」を記録する。1台につき1回だけ（`recorded` 集合で重複防止）。
3. **赤の終了** … その道路が**青になった瞬間**（前フェーズ != green かつ 今 == green）。
4. **確定** … 赤の実時間 `red_dur = red_end - red_start` を**2等分**し、各区間に入る
   初停車台数を数え、最後に **`ceil(台数 / divisor)`** で1車線あたりに直す。

```python
counts = [0, 0]
half = red_dur / 2
for st in stop_times:                 # 赤開始からの経過秒
    idx = min(int(st // half), 1)     # 赤終了ちょうどの車は最終区間へ丸める
    counts[idx] += 1
counts = [math.ceil(c / divisor) for c in counts]
```

> **重要**: 学習データもまったく同じ方法（初停車時刻のビン分け）で作られている。
> 「赤中の各ステップで停車している台数（＝待ち行列長・累積）」とは**別の量**なので、
> 待ち行列長を入力すると分布がずれて予測が当たらない。
> 旧2分割制御は「赤開始から固定オフセット（道路1: +28s/+56s、道路5: +45s/+90s）の
> 瞬間に停車中の台数を数える」方式だったが、これはサイクル長130s固定が前提であり、
> 時間帯別サイクル（100/110/130s）では赤の別の位置を測ってしまうため廃止した。

### 2. GNN による予測

**トリガ**: ある道路の赤が確定し、かつ**9道路すべての2分割が1回以上確定済み**のとき。
道路1と道路5はそれぞれ自分の赤が終わるたびに、独立したタイミングで予測・制御する
（＝2つの制御は同期していない）。

**モデル構造**（学習スクリプト `予測/★予測モデル作成_待ち台数_赤2分割.py` と一致必須）:

```python
class RedSplitPredictionGNN(nn.Module):
    def __init__(self, num_node_features=2, horizon=2, dropout_rate=0.2):
        self.conv1   = GCNConv(2, 64)
        self.conv2   = GCNConv(64, 128)
        self.conv3   = GCNConv(128, 128)
        self.skip    = nn.Linear(2, 128)      # スキップ接続
        self.lin_out = nn.Linear(128, 2)      # t3, t4 を同時出力

    def forward(self, x, edge_index):         # x: [9,2]
        h = F.relu(self.conv1(x, edge_index))
        h = F.relu(self.conv2(h, edge_index))
        h = F.relu(self.conv3(h, edge_index))
        h = h + self.skip(x)
        return self.lin_out(h)                # [9,2]
```

- ノードは道路1〜9 の **9ノード**（`node i = road i+1`）
- `edge_index` は `予測/新環境_隣接行列.csv`（shift-jis, `index_col=0`）の非ゼロ要素から構築
- 重みは `予測/予測モデル/1. 赤時間2分割/道路{1,5}_分散評価あり/GCN_epoch_best_model.pth`
- スケーラは同フォルダの `scaler_wait.pkl`（`MinMaxScaler`。**9道路を特徴量として** fit 済み）

**推論手順**（学習時と完全に一致させること）:

```python
arr = wait_9x2                                   # [9,2] 実台数
# 1) 前半・後半の列ごとに、9道路ベクトルとして正規化
scaled = np.stack([scaler_wait.transform(arr[:, k].reshape(1, -1)).reshape(-1)
                   for k in range(2)], axis=1)   # [9,2]
x = torch.tensor(scaled, dtype=torch.float)
# 2) 対象道路のノードだけ ALPHA 倍して強調（ALPHA = 2）
x[target_node_index] *= 2
# 3) 推論
out = model(x, edge_index).numpy()               # [9,2] 正規化値
# 4) 対象ノードの行だけ逆正規化
o  = out[target_node_index]
mn = scaler_wait.data_min_[target_node_index]
mx = scaler_wait.data_max_[target_node_index]
pred = o * (mx - mn) + mn                        # [t3, t4] 実台数
```

`target_node_index` は 道路1 → **0**、道路5 → **4**。
出力 `[t3, t4]` は **次サイクルの赤の前半／後半に停まる台数**（区間ごとの値。累積ではない）。
**負の値が出ることがある**ので、使う側で 0 下限を入れる。

### 3. delta（青の増減秒数）の計算 ― 需要重み付け方式

```python
GREEN_DEV_START = -10.0     # 予測台数0のときの BASE からのずれ
X1_DEFAULT      = 0.99      # 前半(t3)の重み
X2_DEFAULT      = 0.9       # 後半(t4)の重み
DELTA_CLAMP     = 10

def delta_red2_weighted(t34, x1, x2):
    t3 = max(0.0, float(t34[0]))
    t4 = max(0.0, float(t34[1]))
    delta = GREEN_DEV_START + (t3 * x1 + t4 * x2) * 2.0
    return int(round(max(-10, min(delta, 10))))
```

考え方は「**ギャップ感応制御と同じ起点（基準青 −10s）から、予測需要ぶんを積み上げる**」:

| 重み付き台数 `t3*x1 + t4*x2` | delta | 実際の青 |
| --- | --- | --- |
| 0台 | −10s | BASE − 10s（ギャップ感応の最小青と同じ） |
| 5台 | 0s | BASE ちょうど |
| 10台以上 | +10s | BASE + 10s（上限。以降クランプ） |

制約（`validate_weights`）:

- `x1 > x2` 必須（赤の前半に停まる車＝長く待つ車を優先する）
- 通常は `0 < x1 < 1`、`0 < x2 < 1`
- ピーク時間帯に限り `x1` は `X1_MAX_PEAK = 1.5` まで許容（環境変数 `R2_X1_PEAK`）。
  ただし**実験では効果がなかった**ので既定ではピーク強化しない。

> 旧ルール（比較用に `delta_red2()` として残置、`R2_RULE=old` で選択）:
> `t3 > t4 → +t3*2` / `t3 < t4 → -t4*2` / 同数 → 0、最後に ±10s クランプ。
> **旧ルールは制御なしより悪化する**ので使わないこと。

### 4. 可動範囲へのクランプ

**2段のクランプ**をかける。目標サイクル長が 100s でも 130s でも、ずれの上限は
**絶対秒数で一定**。

| 対象 | 上限 | 定数 |
| --- | --- | --- |
| 各青フェーズの「その時間帯のスケジュール青」からのずれ | ±10s | `J_GREEN_DEV_CLAMP` |
| J のサイクル長の「目標サイクル長」からのずれ | ±10s | `J_CYCLE_DEV_CLAMP`（`R2_CYCLECAP`） |
| 青の絶対下限 | 5s | `J_MIN_GREEN` |

phase0 と phase5 は独立に制御されるため、放っておくと両方が同じ向きに振れて
サイクル長のずれが ±20s になる。そこで **もう一方のフェーズが既に使っている
delta を差し引いて**枠内に収める。

```python
def clamp_delta_for_cycle(phase_idx, delta):
    other = 5 if phase_idx == 0 else 0
    od = j_applied_delta[other]            # もう一方が今入れている delta
    lo = max(-10, -10 - od)
    hi = min( 10,  10 - od)
    if lo > hi:                            # 相手が枠を使い切っている
        return 0
    return int(max(lo, min(delta, hi)))
```

**切り詰めた分は累積に乗せない**（実際に適用した量だけを累積する）。

```python
raw = delta
delta = clamp_delta_for_cycle(phase_idx, delta)
if delta != raw:
    j_cumulative[phase_idx] += delta - raw    # 入れられなかった分を打ち消す
```

### 5. 調整サイクル（サイクル長ドリフトの補正）

delta を入れ続けるとサイクル長がずれていくので、累積が閾値に達したら
**予測を無視して固定量を押し戻すサイクル**を割り込ませる。

```python
OFFSET_ADJUST_THRESHOLD = 20   # 累積 ±20s で調整開始
OFFSET_ADJUST_PER_CYCLE = 10   # 1回の補正量（可動範囲の上限と一致させる）
```

**状態は青フェーズごとに独立**（`j_cumulative = {0:0, 5:0}`、`j_adjust_pending = {0:False, 5:False}`）。

```python
if j_adjust_pending[p]:
    # 調整サイクル: 予測を使わず固定量で押し戻す
    delta = -10 if j_cumulative[p] > 0 else +10
    j_adjust_pending[p] = False
    j_cumulative[p] += delta
    if abs(j_cumulative[p]) >= OFFSET_ADJUST_PER_CYCLE:   # 10s未満になるまで継続
        j_adjust_pending[p] = True
else:
    # 通常サイクル
    delta = delta_red2_weighted(t34, x1, x2)
    j_cumulative[p] += delta
    if abs(j_cumulative[p]) >= OFFSET_ADJUST_THRESHOLD:   # 次サイクルを調整に予約
        j_adjust_pending[p] = True
```

**開始の閾値は20s、終了の閾値は10s**（ヒステリシス）。1回に10sしか戻せないので、
20s 溜まったら通常は調整が2サイクル連続する。

動作例（道路1・100sサイクル・BASE 53s、実走行ログより）:

| # | 種別 | delta | 実際の青 | 累積 |
| --- | --- | --- | --- | --- |
| 4 | 通常 | −8 | 45s | −14 |
| 5 | 通常 | −7 | 46s | **−21** ← 閾値到達、次を調整に予約 |
| 6 | **調整** | **+10** | 63s | −11 ← まだ10s以上あるので継続 |
| 7 | **調整** | **+10** | 63s | −1 ← 10s未満で終了 |
| 8 | 通常 | −1 | 52s | −2 ← 通常制御に復帰 |

調整サイクルの割合は24時間走行で**約35%**。この間は予測が効いていない。

### 6. 青時間への反映

```python
dur = max(5.0, j_scheduled_green[phase] + j_applied_delta[phase])
```

**毎サイクル「スケジュール青 + delta」で上書きする**（前サイクルの結果に足し込む
＝ compound はしない）。他のフェーズ（黄・全赤・右折矢印）の長さは変えない。
`traci.trafficlight.setProgramLogic("J", logic)` で書き戻す。

### 7. 時間帯別サイクル長

```python
BASE_CYCLE_LENGTH = 120     # net.xml の基準サイクル
PREP_CYCLE_LENGTH = 100     # 準備時間中
PREP_TIME         = 1200    # 準備(warmup)秒数。sim_time = 1200 が 0時0分
CYCLE_SCHEDULE_BY_HOUR = [
    (0,  7, 100),   # 0〜7時
    (7,  8, 130),   # 7〜8時（朝ピーク）
    (8, 17, 110),   # 8〜17時
    (17,19, 130),   # 17〜19時（夕ピーク）
    (19,24, 100),   # 19〜24時
]
```

**J のスケジュール青**は、120sネットの基準青 `{phase0: 63.0, phase5: 29.0}` に
`(目標サイクル − 120) / 2` を各青へ均等配分して作る。

| 目標サイクル | phase0（道路1） | phase5（道路5） | 可動範囲 |
| --- | --- | --- | --- |
| 100s | 53s | 19s | 43〜63s / 9〜29s |
| 110s | 58s | 24s | 48〜68s / 14〜34s |
| 130s | 68s | 34s | 58〜78s / 24〜44s |

**J 以外の信号**は `build_scaled_logic()` で、**10秒以上の青フェーズにのみ**
`(目標サイクル − 基準サイクル) / 青フェーズ数` を均等配分する（黄・全赤・
10秒未満の右折矢印は固定）。フェーズ数・状態・順序・番号は変えない。
**基準サイクルが120sの信号だけが対象**で、それ以外（交差点C = 90s 固定、
J50・1677890329 = 90s）は無言でスキップされる。

### 8. 比較対象: ギャップ感応制御

提案手法と**同一の枠（BASE ± 10s）**に収めることで条件を揃えている。

| 項目 | 値 |
| --- | --- |
| 開始時の青（最小青） | **BASE − 10s**（100sサイクルなら 主道路43s / 従道路9s） |
| 最大青 | BASE + 10s（かつサイクル長の枠で更に絞る） |
| ギャップ閾値 `MAX_GAP` | **5秒** |
| 感知器 | 主道路 `J_south_1` / 従道路 `J_west_0`（ループコイル、停止線5m手前） |

```python
# 青の開始時
allotted = MIN_GREEN                      # = BASE - 10s
# 青の最中（毎ステップ）
if green_time >= MAX_GREEN:
    traci.trafficlight.setPhase(tls, phase + 1)      # 保険として強制的に切る
elif 感知器に車がいる:
    allotted = min(green_time + MAX_GAP, MAX_GREEN)  # 「今から5秒先」まで延長
# 割当が尽きた（＝5秒の隙間が空いた）ら次現示へ
```

- `setPhaseDuration` は**次ステップから効く**ため、指令値から
  `GREEN_STEP_OFFSET = 1`（秒）を引いて実際の青が狙いどおりになるようにする。
- 累積オフセット補正（調整サイクル）は予測制御と**同じ方式・同じ閾値**で入っている。
  ただし偏差は指令値ではなく**実測の青**から測る: `偏差 = 実際の青 − 青開始時点のBASE`。
- 偏差の基準 BASE は**青の開始時点の値を控えて**使う（`main_base_at_start`）。
  時間帯別サイクル長の切替が青の途中で起きると基準が変わり、偏差が枠を超えるため
  （修正前は +25s の例があった）。

### 10. 再実装時に間違えやすい点

1. **入力は「初停車時刻のビン」であって「待ち行列長」ではない。** 取り違えると
   学習時と分布がずれて予測が当たらない。
2. **9道路すべての計測が要る。** 制御対象の1・5だけでは `[9,2]` が作れない。
3. **正規化は「9道路を特徴量として」列ごとに掛ける。** サイクル方向ではない。
4. **ALPHA 倍は正規化の後**、対象ノードの行にのみ掛ける。
5. **逆正規化は対象ノードの `data_min_` / `data_max_` を使う。**
6. **予測値は負になりうる。** delta 計算前に 0 で下限を切る。
7. **delta は毎サイクル「スケジュール青 + delta」で上書き**。前回値に足し込まない。
8. **道路5の青は phase 5**（phase 6 は常に3秒の現示で、青ではない）。
9. **準備時間(1200s)中は累積も計測もしない。** 開始直後の1本目の青は traci 接続時に
   既に進行中だった位相の残りなので、偏差が過大に出て累積を汚す。
10. **赤2分割モデルの学習データは130s固定サイクルで作られている。** 制御時の
    時間帯別サイクル（100〜130s）とは条件が違う。モデルは「赤を2等分した各区間の
    台数」を見るので比は保たれるが、厳密に揃えたい場合は `CYCLE_SCHEDULE_BY_HOUR` を
    全時間帯130sにして、比較対象（none / gap）も同条件で回し直すこと。

### 赤の分割の測り方（両方式で共通）

1. その道路の**黄が終わった瞬間**を赤開始、**青になった瞬間**を赤終了とする（フェーズ番号で判定）。
2. 赤の間、対象エッジで**初めて速度0になった車**の「赤開始からの経過秒」を記録する。
3. 赤終了時に赤の実長を2等分（3分割版は3等分）し、各区間の初停車台数を数え、`ceil(台数/2)` する。

旧2分割制御（`1. 信号制御用_従道路も.py`）は「赤開始から固定オフセット（道路1: +28s/+56s、
道路5: +45s/+90s）の瞬間に停車中の台数を数える」方式だった。この固定値は**サイクル長130s固定**を
前提にしたもので、時間帯別サイクルでは赤の別の位置を測ってしまうため、実測赤を等分する方式に変えた。
赤の間は車が列から出ていかないので「その時点で停車中の台数」≒「そこまでに初停車した台数」であり、
定義の差は前サイクルの残留車と微速前進車の扱いだけ。

## ギャップ感応制御の仕様（2026-08-03 確定）

**最小青から始めて、車が来る限り延長する**方式。予測制御と同じ ±10s の枠に収まる。

| 項目 | 値 |
| --- | --- |
| 開始時の青（最小青） | **BASE − 10s**（100sサイクルなら 主道路43s / 従道路9s） |
| 最大延長幅 | **20s**（最小青 → BASE + 10s） |
| 延長のしかた | 感知器に車が来るたび「今から `MAX_GAP` = 5秒先」まで割当を伸ばす（上限 MAX） |
| 終了条件 | 割当が尽きたとき（＝5秒の隙間が空いたとき）／MAX 到達時は強制的に切る |
| 感知器 | 主道路 `J_south_1` / 従道路 `J_west_0`（ループコイル） |

BASE = その時間帯のスケジュール青（`j_scheduled_green`）。予測制御の `スケジュール青 + delta` と
同じ基準なので、両方式とも「BASE ± 10s」という同一条件で比較できる。

### 累積オフセット補正（サイクル長のドリフト補正）

青が終わるたびに `偏差 = 実際の青 − BASE` を累積し、閾値に達したら調整サイクルで押し戻す。
予測制御とまったく同じ方式・同じ閾値（20s で開始、10s 未満になるまで継続、1回の補正 ±10s）。

```text
延長なしが続く場合（100sサイクル・主道路 BASE=53s）
  43s → 偏差 -10 → 累積 -10
  43s → 偏差 -10 → 累積 -20   ← 閾値到達、調整サイクルを予約
  63s → 偏差 +10 → 累積 -10   ← 調整（BASE+10s）。10s以上なので継続
  63s → 偏差 +10 → 累積   0   ← 通常に復帰
```

偏差の基準 BASE は**青の開始時点の値を控えて**使う（`main_base_at_start`）。
時間帯別サイクル長の切替が青の途中で起きると BASE が変わり、
「割り当てたときの基準」と「測るときの基準」が食い違って偏差が枠を超えるため
（修正前は +25s の例があった）。

## 時間帯別サイクル長の対象信号

基準サイクルが120sの信号だけが時間帯別スケーリングの対象。それ以外は対象外として
**無言でスキップ**される（`5. 信号制御_赤2分割.py` の `abs(base_cycle - 120) > 0.5: continue`）。

| 信号 | 基準サイクル | 時間帯別サイクル長制御 |
| --- | --- | --- |
| A, B, D, E, F, G, H, I, K, L, M, N, O, P | 120s | 対象（100 / 110 / 130s に切替） |
| J | 120s | 対象（GNN制御・ギャップ制御側で個別に適用） |
| **C** | **90s** | **対象外 — 常に90s固定** |
| J50, 1677890329 | 90s | 対象外 |
| cluster_… 5信号 | 120s | 対象 |

C だけは元から90s設計なので、他が100/110/130sに動いても90sのまま。3分割版も同じ挙動。

## 制御モード（`R2_MODE` / `R3_MODE`）

| モード | 内容 | 使う予測 |
| --- | --- | --- |
| `prediction` | GNN予測で青を伸縮（既定） | 赤2分割 or 赤3分割モデル |
| `gap` | ギャップ感応制御（車頭時間が空いたら青を切る） | 使わない |
| `none` | 制御なし（固定サイクル）。計測とログだけ | 使わない |
| `pgap` | ギャップ骨格 + 予測Nでギャップ閾値を動的に緩める | 到着間隔モデル(W・N) |
| `pgapmin` | 予測WでMIN_GREENを可変にする版 | 到着間隔モデル(W・N) |
| `npred` | ギャップを見ず「通過台数 ≧ 予測N」で青を切る | 到着間隔モデル(W・N) |

`pgap` / `pgapmin` / `npred` は赤の分割数に依存しない（道路ごとの**合計**待ち台数とNしか使わない）ため、
2分割版でもそのまま動く。

## 時間距離図の作り方（注目サイクルの切り出し）

「この時間帯でなぜ差がついたのか」を車両軌跡で確認する手順。
**シミュレーションは方式ごとに1回だけ**でよい。軌跡をCSVに残すので、
サイクルや表示区間を変えたくなっても再実行は不要。

### 手順1: 軌跡を記録しながら走らせる（方式ごとに1回）

```bash
cd 制御/新環境用

# ギャップ感応
R2_MODE=gap        R2_SUFFIX=_時間距離図 R2_END=58800 python "5. 信号制御_赤2分割.py"
# 提案手法
R2_MODE=prediction R2_X1=0.99 R2_X2=0.9 R2_SUFFIX=_時間距離図 R2_END=58800 python "5. 信号制御_赤2分割.py"
```

| 環境変数 | 意味 |
| --- | --- |
| `R2_TSWIN` | 記録する時間窓 `"開始-終了,開始-終了"`。既定は `22500-26400,54900-58800`（6時台と15時台。頭に300sのリードイン付き） |
| `R2_END` | 打ち切り時刻。**最後の窓が終わる時刻でよい**（15時台までなら 58800＝16時） |
| `R2_SUFFIX` | 出力フォルダ名の接尾辞。**必ず指定する**（途中で打ち切った集計で既存の24h結果を潰さないため） |

`sim_time = PREP_TIME(1200)` が 0時。したがって **N時 = 1200 + N×3600**。

出力は `csv掃き出し/赤2分割/<方式>_時間距離図/` に:

```text
実行ログ.txt                       ← 自動保存。通常/調整サイクルと delta が入っている
時間距離図/
├── 時間距離図_<窓>.png            ← 窓ごとの全体図（自動保存）
├── 軌跡ログ.csv                   ← 車両軌跡（dir, sim_time, veh, edge, pos, x）
├── 赤信号区間.csv                 ← 交差点ごとの赤時間帯
├── J毎秒_待ち遅れ.csv             ← サイクル特定用
└── 交差点位置.csv                 ← 距離軸上の交差点位置
```

**再現性の確認**: 途中で打ち切った実行の `時間帯別_signal方式_遅れ待ち_青サイクル.csv` が、
既存の24h実行と一致するか見ておく。一致すれば同じ挙動を切り出せている
（2026-08-05 の実行では 0〜14時が両方式とも完全一致）。

### 手順2: 注目サイクルを切り出して描く

```bash
python "★赤2分割_時間距離図_サイクル抽出.py"
```

やること: Jのサイクル境界を作る → 毎秒データをサイクル単位で集計 → 2方式を開始時刻で
突き合わせる → 指定時間帯で差が最大／最小のサイクルを選ぶ → 前後Nサイクルを描く。

出力は `csv掃き出し/赤2分割/時間距離図_比較/` に図4枚と `サイクル別_方式間差.csv`、
各方式フォルダに `制御サイクルログ.csv`。

### 調整できる箇所（スクリプト先頭）

| --- | --- |

- 実行ログは手順1で自動保存される。**手動でコピーしてきたログでも動く**が、

## 既知の注意点

1. **予測モデルのパスは修正済み（2026-08-02）。**
   フォルダを 計測 / 予測 / 制御 の3構成に整理した際、予測モデルが `研究/予測モデル/` から
   `研究/予測/予測モデル/` へ移動したが、`赤3分割_制御コア.py` と `到着間隔_制御コア.py` の
   `_PRED_ROOT` が旧パスのままで **`load_road_model` が FileNotFoundError になっていた**。
   両方とも `"予測", "予測モデル", …` を経由するよう修正済み。

2. **赤2分割モデルは130s固定サイクルで学習されている。**
   学習データ（`新環境待ち台数データ_12.22.csv`, 665サイクル/日 = 130s）と、制御時の
   時間帯別サイクル（100〜130s）は条件が異なる。モデルは「赤を2等分した各区間の台数」を
   見るので比は保たれるが、厳密に学習条件へ合わせたい場合は `赤3分割_制御コア.py` の
   `CYCLE_SCHEDULE_BY_HOUR` を全時間帯130sにして、比較対象（none/gap）も同条件で回し直すこと。
   赤3分割モデルの学習データは時間帯別サイクルで計測されているのでこの問題は無い。

3. **2分割の delta は青を延長する側に偏る。**
   学習データのテスト日で試算すると delta の平均は 道路1 = +3.5s、道路5 = +3.0s
   （道路5は664サイクル中、負の delta が0回）。赤の前半に多く停まるという物理的傾向によるもの。
   旧2分割制御が偶数サイクルで打ち消していたのはこの偏りを相殺するためと思われる。
   既定の累積オフセット補正でもドリフトは抑えられるが、挙動を比べたい場合は `R2_EVENCANCEL=1`。

4. **ギャップ感応制御の青がサイクル長に追従していなかった（2026-08-02 修正）。**
   `GapCycleController` は BASE/MIN/MAX を 60/50/70s（主道路）・26/16/36s（従道路）で
   **固定**しており、さらに時間帯別サイクル長の切替時に J だけスケジュール青の更新を
   スキップしていた。そのため他の信号が100sサイクルに切り替わっても **J のギャップ制御だけ
   120s基準の青のまま**で、サイクル長が食い違っていた。
   現在は `_refresh_bounds()` が各青の開始時とサイクル長切替時に
   「その時間帯のスケジュール青 ±10s（かつサイクル ±10s）」を取り直す。
   ※ `pgapmin` / `npred` は独自のMIN/MAXを使うため `follow_schedule = False` で追従対象外。

5. **`train_csv_path` は現在どのスクリプトでも使っていない**（変数として残っているだけ）。

6. 旧スクリプトの多くは**絶対パス直書き**で、`C:\Users\Tsukasa\Desktop\研究\…` を前提にしている。
   現行の `4.` / `5.` とコアモジュールはスクリプト位置からの相対解決。

### 合計で判定する案を試したが不採用（2026-09-18）

`j_cumulative[0] + j_cumulative[5]` が ±20s に達したら調整に入る方式に変更して検証した。
**オフセットずれは狙いどおり抑えられたが、制御性能が大きく悪化したため採用しない。**
実装は ブランチ `fix/adjust-cycle` のコミット `5831ed0` に記録してある。

試した内容:

- 発火判定を主従の累積の**合計**に変更（20s で開始、10s 未満で終了）
- 調整中は主従の**両方**を調整サイクルにする。片方だけだと、同じサイクルのもう一方が
  通常制御で逆向きに振れて相殺し、合計 −115s 付近で膠着した
  （1サイクルで押し戻せる量も自然ドリフトも `clamp_delta_for_cycle` の ±10s が上限で同じため）
- 予約判定をクランプ後に移動（枠制限で空振りした調整が黙って終了する件も解消）
- 比較条件を揃えるためギャップ感応側も同じ方式に統一

結果（24時間走行・基準は制御なし）:

提案手法（x1=0.99 / x2=0.9）:

| 指標 | 修正前 | 修正後 |
| --- | --- | --- |
| 対象交差点J 待ち台数 | **−7.5%** | +1.9% |
| 対象交差点J 遅れ時間 | **−4.3%** | +10.7% |
| 街全体 待ち台数 | +0.3% | +8.4% |
| 街全体 遅れ時間 | +0.2% | **+16.4%** |
| オフセット累積ずれ | −43 〜 +38s | **−20 〜 +0s** |
| \|ずれ\| ≧ 30s の割合 | 11.6% | **0.0%** |

ギャップ感応（同じ修正を入れた対照）:

| 指標 | 修正前 | 修正後 |
| --- | --- | --- |
| 対象交差点J 待ち台数 | **−18.9%** | −10.9% |
| 対象交差点J 遅れ時間 | **−2.4%** | −1.0% |
| 街全体 待ち台数 | −2.2% | −2.5% |
| 街全体 遅れ時間 | +1.5% | −0.7% |

ギャップ感応も対象交差点では悪化したが、街全体はわずかに改善しており大崩れはしていない。
**影響は提案手法のほうが桁違いに大きい**（街全体の遅れ +0.2% → +16.4%）。
予測に基づく delta は調整サイクルに置き換えられると情報が丸ごと失われるのに対し、
ギャップ感応はもともと「最小青から車が来る限り延ばす」だけなので失うものが少ないためと考えられる。

悪化した理由:

- delta の全体平均が **道路1 +0.02s / 道路5 −0.03s（ほぼ中立）** から
  **道路1 +3.59s / 道路5 −3.57s** へ変わり、制御が「恒常的なスプリット変更」に変質した。
  フェーズ別の調整は**スプリット偏りを抑える働きも兼ねていた**ため、
  それを外したことで従道路の青が常時3.6s削られ、街全体へ波及した。
- 主従が同一サイクルで同時に調整へ入る回数が **92回 → 254回** に増え、
  両道路とも予測が効かないサイクルが増えた（調整サイクルの総数自体は 34.8% → 35.9% とほぼ同じ）。

したがって「オフセットずれを抑える」と「予測制御を効かせる」はトレードオフの関係にある。
ずれ自体を抑えたい場合は、押し戻し量を ±10s より小さくする、フェーズ別判定を残したまま
合計にも上限を足す、といった弱い介入から試すこと。
